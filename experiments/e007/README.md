# Public Work Sample Candidate — Timing Artifacts Can Flip Multi-Agent Cooperation Classifications

**Status:** public synthetic work sample. **Released executable sample; license scope: [LICENSE_STATUS.md](LICENSE_STATUS.md).**

**Project:** Project Intersection / RGBM Lab

**Scope:** evidence of falsification-first research behavior and reproducible toy-model sensitivity. It is **not** evidence that real-world coexistence is solved.

## One-sentence result

In a small finite-horizon multi-agent toy game, changing the timing semantics alone changed history and/or classification in **36 of 72 synthetic audit cases** and changed the outcome classification in **17 of 72**, showing that an apparently favorable cooperation result can depend on who is allowed to act first rather than on a robust property of the mechanism.

These are **synthetic sensitivity counts, not empirical probabilities**.

## Minimal research question

> Does an apparent cooperation/exit outcome remain the same when the same state is evaluated under two reasonable timing conventions?

The audit compares:

1. **exit-priority timing** — a valid exit can resolve before a same-period hostile action;
2. **execute-first timing** — a committed hostile action can execute before the target's same-period response.

The goal is not to declare one timing convention universally correct. The goal is to reject conclusions that depend on silently choosing one.

## What failed during audit

The first timing sweep itself contained a role-reversal bug: in B-leading cases it varied B's exit coordinate when the intended target was A. Therefore part of the original role-reversal audit was not symmetric.

The error was preserved, corrected, regression-tested, and rerun as `kf002-v2-target-symmetric`.

A later history-encoding audit found a second, narrower defect: under execute-first timing the solver recorded the follower's effective action from the **pre-strike** state even when the strike had already rendered that follower inactive before its response. Utilities and classifications were unchanged, but the history representation violated the inactive-actor rule. The repaired encoding records the follower from the post-strike response state. This changes the history/timing-sensitive count from **31/72 to 36/72** while the classification-sensitive count remains **17/72**.

### Corrected 72-case result

| Audit result | Count | Share of selected synthetic grid |
|---|---:|---:|
| Any history and/or classification changed | 36 / 72 | 50.0% |
| Outcome classification changed | 17 / 72 | 23.6% |
| A-leading timing-sensitive | 18 / 36 | 50.0% |
| B-leading timing-sensitive | 18 / 36 | 50.0% |
| A-leading classification-sensitive | 8 / 36 | 22.2% |
| B-leading classification-sensitive | 9 / 36 | 25.0% |

The percentages describe only the chosen toy audit grid.

## Defensible interpretation

The result does **not** mean that 23.6% of real cooperative systems are timing-fragile.

The supported claim is narrower:

> Within the stated toy benchmark, a substantial subset of classifications is not invariant to a plausible timing change. Timing semantics must therefore be treated as a promotion blocker rather than hidden implementation detail.

This is primarily a falsification result about the benchmark itself.

## Reproducibility design

The publication candidate is generated by an allowlist-based build step rather than by copying the whole private repository.

The configured verification path checks:

- the full project regression/governance suite;
- construction of an isolated E007 candidate;
- **27 isolated E007 regression tests**;
- rerunning the timing probe from that isolated directory;
- exact reproduction of **72 total / 36 timing-sensitive / 17 classification-sensitive**;
- a conservative credential/personal-pattern scan;
- automatic generation of provenance, run instructions, minimal dependencies, license-status note, and machine-readable timing output.

The build fails if the headline 72/36/17 counts change without review.

Each generated bundle's exact source commit belongs in its generated `PROVENANCE.md`; its archive digest belongs in the external build/execution record. They are intentionally **not self-pinned inside this README**, because embedding an archive's own digest or a later commit identifier in a file inside that archive creates a circular, stale provenance problem.

Green CI and isolated reproducibility show that the configured artifact behaves reproducibly. They do **not** establish scientific truth, external validation, or frontier-model safety.

## Research behavior demonstrated

1. A cooperation-oriented result existed.
2. Its implementation assumptions were attacked.
3. Timing dependence was found.
4. The first audit of that dependence was itself found to contain a role-reversal bug.
5. The audit was corrected rather than discarded.
6. The corrected result remained materially timing-sensitive.
7. The correction became regression and CI coverage.
8. The claim was narrowed instead of turning the failure into a success narrative.

The intended research loop is:

`claim -> rival -> attack -> failure -> correction -> regression test -> narrower claim`

## Stronger evidence still missing

Do not treat E007 as a validated cooperation benchmark while these remain unresolved:

- stochastic detection and delayed enforcement rather than deterministic/scalar punishment;
- robustness to tied best responses and equilibrium selection;
- state-by-state participation/voluntariness rather than only end-to-end value checks;
- copy/substitution baselines;
- omitted-stakeholder and third-party-harm cases;
- independent external reproduction or adversarial review;
- learned-agent evaluation only after the toy semantics are stable enough to justify it.

## Kill criteria for the next stage

Narrow or kill the construct if:

1. timing/equilibrium variants erase the distinction between voluntary cooperation and coerced continuation;
2. a simpler baseline explains the same rankings;
3. practical-exit constraints never change a decision-relevant result outside hand-picked payoffs;
4. the benchmark can be gamed while destroying the property it claims to measure;
5. external reviewers cannot reproduce the result from the released package;
6. learned-agent testing eventually exposes no stable behavior that the benchmark distinguishes.

## Fastest reviewer attacks

A reviewer can help by:

- proposing a third timing convention that makes both current variants misleading;
- showing that a different equilibrium-selection rule removes the sensitivity;
- identifying a stronger baseline that makes the classification distinction unnecessary;
- finding a state where formal exit exists but practical exit has already been destroyed;
- finding a role-reversal failure caused only by labeling or turn order;
- reproducing the 72-case audit and reporting any mismatch.

A successful attack that weakens the result is a successful research outcome.
